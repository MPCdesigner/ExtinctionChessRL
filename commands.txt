== BENCHMARK TESTS (submitted from cluster shell after SSH) ==

The 4-test battery run after each new 100% checkpoint (checkpoints exist only
at multiples of 10).

PREFERRED — use trpro-slurm2 (RTX 4090). It is isolated from training
(main = delta-slurm1, helpers = trpro-slurm1), so tests never contend
with helpers for CPU cache / memory bandwidth. Verified working Jul 7.

FALLBACK — trpro-slurm1 (RTX 3090). Only use if trpro-slurm2 is down.
On trpro-slurm1, MUST add --nice=10000 so pending helpers always outrank
pending tests. Even with --nice, running tests block helper allocations
until they finish, and MCTS-heavy tests running alongside helpers cause
2-3x slowdown for both. Prefer waiting for auto-resubmit gaps between
main jobs.

Filename convention on cluster: az_iter_<N>_<WIN_PCT>pct.pt
  - Most are _100pct.pt
  - Known exceptions: iter 550_98pct.pt, iter 690_98pct.pt
  - Verify before running: ls ~/extinction-chess/models/ | grep -E "az_iter_(N|ANCHOR|100)_"

Anchor convention for Test 4: previous checkpoint that was last benchmarked
with the FULL 4-test battery, NOT necessarily the most recent 100%. Example:
iter 720 was benchmarked with iter 680 as anchor (iter 690, 700, 710 were
skipped in-between).

--- Test 1: WIN-TAKING (multi-model, ~10 min on trpro-slurm2 clean) ---
Given 200 forced-win positions, does each model find the winning move at
20/50/100/200 sim depth? Higher % = better tactical play.

Model list covers ~24 checkpoints spanning last ~240 iters + 340 + 100.

--- Contention notes ---
  - Prefer trpro-slurm2 (isolated from training). Verified Jul 7.
  - On trpro-slurm2, --nice is optional — nothing to contend with.
  - Trpro-slurm1 fallback contention: tests running alongside helpers
    experience 2-3x slowdown due to shared CPU L3 cache and memory
    bandwidth. Both tests AND helpers get slower. Avoid unless necessary.

    test never blocks a helper waiting to allocate a GPU.
  - Retroactive nice bump on a pending job: scontrol update jobid=<ID> nice=10000

== AUTO-BENCHMARK BATTERY (fires automatically on every ×10 checkpoint) ==

After every multiple-of-10 iter save, main automatically launches 13 test
jobs + 1 aggregator on trpro-slurm2. Non-blocking — main continues to next
iter immediately. Aggregator runs after all tests complete (5-6h later)
and writes a single human-readable summary file.

Controlled by benchmark_enabled=True in ~/extinction-chess/src/run_training.py
(inside the train(...) call). See memory: benchmark_automation.

--- What runs ---
  1. 5 recent H2H tests (vs iter N-10, N-20, N-30, N-40, N-50)
  2. 5 distant H2H tests (vs iter N-110, N-120, N-130, N-140, N-150)
  3. Win-taking multi-model (recent + distant + fixed anchors 560,550,540,
     520,500,480,340,100)
  4. Tactical random test
  5. vs iter 100 baseline H2H
  6. Aggregator (sbatched with --dependency=afterany on all 13 tests)

Missing reference checkpoints are silently skipped.

--- View the aggregated summary ---

  cat ~/extinction-chess/benchmark_results/iter_<N>.txt

  # For example, for iter 780:
  cat ~/extinction-chess/benchmark_results/iter_780.txt

Summary format is a concatenation of each test's own end-of-log block, with
section headers "[i/13] category: subject (job JOBID)". Matches exactly what
raw tests print, so it's readable without regex parsing.

--- View a specific test's raw log ---

  # Individual per-test logs live in a sub-directory per iter:
  ls ~/benchmark_battery/iter_<N>/

  # Contents include:
  #   compare_<N>vs<opp>_<jobid>.log    (10 H2H logs, one per opponent)
  #   bench_win_taking_<jobid>.log      (win-taking log)
  #   tactical_<N>_<jobid>.log          (tactical random)
  #   compare_<N>vs100_<jobid>.log      (vs iter 100)
  #   aggregator_<jobid>.log            (aggregator's own log)

  tail -30 ~/benchmark_battery/iter_780/compare_780vs720_XXXXX.log

--- Verify a battery fired for a given iter ---

  # 1. Look for the "[benchmark]" lines in main's log around iter N:
  grep -A 20 "\[iter <N>\]" ~/train_<jobid>.log

  # Expected: 14 "[benchmark]" lines after the "★ new best" line —
  # one per test job launched, plus aggregator.

  # 2. Verify the summary file exists (appears ~5-6h after iter save):
  ls -la ~/extinction-chess/benchmark_results/iter_<N>.txt

  # 3. If not there yet, check remaining test jobs still running:
  squeue -u h74liang | grep trpro-slurm2

--- Rolling-window model list (recent + distant) ---

At iter N, the recent-5 opponents are iter N-10 through N-50, and the
distant-5 are iter N-110 through N-150. The lists shift by 10 for each
new benchmark. Win-taking always includes these 10 rolling opponents PLUS
the fixed anchors 560,550,540,520,500,480,340,100. Fixed anchors let us
compare current strength against historically-important checkpoints
without them being "aged out" of the rolling window.

--- Interpretation cheat sheet ---

  H2H % > 55%      → new checkpoint clearly stronger than opponent
  H2H % ~ 50%      → tied within noise (200 games has ±7% CI)
  H2H % < 45%      → new checkpoint clearly weaker (regression)

  Win-taking       → tactical acuity metric. iter 500-560 tops it due to
                     Phase-13 drilling artifact. NEVER use in isolation.

  Tactical random  → general play metric. Complements win-taking.

  vs iter 100      → baseline sanity check. Should be 65%+ for any
                     mature checkpoint.

--- Enable / disable ---

  # Check current state:
  grep benchmark_enabled ~/extinction-chess/src/run_training.py
  # (must be in ~/extinction-chess/src/ NOT ~/extinction-chess/ — see the
  # "Upload a file to cluster" section above for the path trap)

  # To disable temporarily: edit the file, set to False, SCP to src/,
  # takes effect at next auto-resubmit.


== POSITIONAL EVALUATION TOOL (local, pygame) ==

Local tool for inspecting how specific models evaluate specific positions.
Complements the aggregate benchmark battery — battery gives statistics,
this gives per-position insight.

  cd "c:\Users\henry\Desktop\Extinction Chess RL"
  python -m tools.positional_eval

Startup opens a tkinter file picker — multi-select model .pt files from
models/. Once loaded, main window (1500×940) opens with:
  - Board (left)
  - Palette (only in construction mode)
  - Model columns (right)
  - Controls: 2-row (main row + value-gen row when toggled)
  - Settings overlay (Max sims / Models / Display options / MCTS params)

Values are displayed in WHITE'S perspective: +1 = White winning, -1 =
Black winning. Does NOT flip with whose turn it is (internally the model
outputs current-player-perspective; the tool converts).

━━ Settings panel sections (top-right button) ━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. Max sim count (radio)
     Which sim counts to evaluate: raw NN, 20, 50, 100, 200, 400, 800,
     unlimited. Runs one MCTS to max(selected) and takes checkpoint
     snapshots — cheaper than one search per sim count.

  2. Include models in evaluation (checkboxes)
     Toggle each loaded checkpoint on/off for the current eval.

  3. Display options (Aug 7-8 additions)
     - [ ] Highlight endangered pieces
        When on, each piece that's the LAST of its type for its color
        gets a red tint on its square. Extinction-chess-specific: losing
        the last piece of a type ends the game, so this surfaces
        tactical stakes at a glance.
     - max moves shown: 20 (default) → 25 → 30 → 35 → 40
        Cyclable button (click to advance). Bump to 40 when you need to
        see rare-move planes (e.g., R/B/K underpromotions that fall
        outside the default top 20).

  4. MCTS parameters (Aug 7 additions)
     Three cyclable-preset rows:
       c_puct:          2.5 (default) / 3.0 / 4.0 / 5.0 / 10.0
       noise_weight:    0.0 / 0.15 / 0.25 (training) / 0.35 / 0.50
       dirichlet_alpha: 0.3 (training) / 0.6 / 1.0 / 2.0
     Purpose: exploration diagnostic — see whether cranking noise/c_puct
     causes normally-collapsed rare-move priors (e.g., R/B/K promotions)
     to become visited.

     Pill coloring (Aug 8 refinement):
       GREY  = value matches TRAINING's setting (not the tool's default)
       ORANGE = value differs from training (diagnostic-only state)
     So all grey = you're evaluating with the same MCTS conditions
     self-play uses. Any orange = you're in exploratory mode and
     results won't reproduce training behavior.

━━ Common exploration diagnostic recipe ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Load an interesting position (e.g., forced-mate promotion).
2. Set max moves shown to 40 (surfaces low-prior legal moves).
3. Evaluate at defaults (all pills grey).
   - If a move you EXPECT to be considered (like a winning
     underpromotion) gets 0 visits at 800 sims → policy-head prior
     for that move is below the UCB exploration threshold (~0.0004
     at c_puct=2.5).
4. Bump exploration (turn all pills orange):
   c_puct=5, noise_weight=0.35, dirichlet_alpha=0.6.
5. Re-evaluate. If the missing move now gets visits → mechanism confirmed.
6. Push c_puct=10, noise_weight=0.5, dirichlet_alpha=2 for maximum
   exploration — see visits recipe from Aug 8 tool session.

━━ Concurrent-instances warning ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Only run ONE instance of the tool at a time. The value-dataset storage
(dataset/value_targets.json) uses atomic-write via tmp + os.replace, but
each process holds its own in-memory session/entry lists. Two concurrent
instances can silently overwrite each other's changes when they both
save. Pure evaluation (no value-gen toggle) is fine because it doesn't
write to the dataset.

See memory: positional_eval_tool for pre-Aug-7 history.


== VALUE DRILLING PIPELINE (hand-curated training data) ==

┌─ STATUS (Aug 5-6 2026) ─────────────────────────────────────────────────┐
│ Feature:  Curate positions in the positional_eval tool → save with     │
│           value target → upload to cluster as an npz that behaves like │
│           self-play data with zero-filled policies.                    │
│ Storage:  dataset/value_targets.json (local, gitignored)               │
│ Export:   tools/build_value_drill_npz.py → iter_9999_valdrill.npz      │
│ Uploaded: SCP to cluster ~/extinction-chess/replay_buffer/             │
│ Effect:   Loaded into training buffer alongside self-play data;        │
│           value MSE hits, policy loss contributes 0 (zero targets).    │
└─────────────────────────────────────────────────────────────────────────┘

━━ Why value-only (not policy) ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The value head is a single scalar — it can't over-memorize hand-authored
positions the way a full 4864-dim policy target could. Previous experiments
with policy drilling caused overfitting; value drilling is structurally
safer. Zero-filled policy target means cross-entropy loss contributes 0
per hand-set sample (no gradient on policy head). Only value MSE hits.

━━ Storage: dataset/value_targets.json ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Managed by tools/positional_eval/value_dataset.py. Data model:

  {
    "sessions": [
      {"session_id": "2026-08-05T22:03:00", "started_at": "...",
       "entry_count": 12},
      ...
    ],
    "entries": [
      {
        "value": 1,                          // -1 / 0 / +1, White perspective
        "tags": ["forced_win"],              // record-keeping only
        "session_id": "2026-08-05T22:03:00", // tool-run identifier
        "added_at": "2026-08-05T22:03:14",
        "position": {                        // PositionState.to_dict()
          "mode": "game_setup",
          "board": [[...]],
          "to_move": "W",
          "en_passant": null,
          "halfmove_clock": 12,
          "fullmove_number": 25,
          "move_history": [...]              // ← replayed at export time
        }
      }
    ]
  }

Key design decisions:
  - Duplicates ALLOWED (some positions worth drilling extra). Warning
    dialog shows per-value breakdown before adding a duplicate.
  - Position identity is SEMANTIC (board+turn+castling+en-passant),
    NOT move_history. See value_dataset._canonical_position_key.
  - Session grouping enables per-session export/rollback (via --session
    flag on the CLI).
  - Move history is preserved in the position dict — on export we replay
    it to reconstruct the C++ Game with correct history-planes,
    castling rights (via has_moved), and en-passant.
  - Tags are metadata ONLY — never seen by training. Extensible: append
    to VALUE_TAGS in value_dataset.py (currently: forced_win, material_adv).

━━ UI workflow in the eval tool ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. Toggle "Value Dataset: OFF" → "Value Dataset: ON | N total | K this session"
     Bottom row expands to show save buttons + tag chips.
  2. Navigate to a position (Game Setup mode — plays a game to reach it).
  3. Click one of: [White wins +1] [Draw 0] [Black wins -1]
     - Value = White's perspective always. NO auto-flip.
     - Optional: click tag chips first ([forced_win] [material_adv]).
       Tags persist across saves until toggled off.
  4. If position already in dataset, warning dialog shows breakdown
     and asks confirm.
  5. Indicator under board shows "In dataset: 2x +1, 1x -1 [tag_name]"
     for the current position (updated live).

━━ Export to cluster-compatible npz ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  python tools/build_value_drill_npz.py                       # all entries
  python tools/build_value_drill_npz.py --dry-run             # counts only
  python tools/build_value_drill_npz.py --tags forced_win     # filter by tag
  python tools/build_value_drill_npz.py --session <ID>        # single session
  python tools/build_value_drill_npz.py -o path/to/file.npz   # custom output

Default output: dataset/iter_9999_valdrill.npz. Naming rationale:
  - "iter_9999_valdrill.npz" matches the buffer regex
    ^iter_(\d+)(?:_([A-Za-z0-9]+))?\.npz$, so the loader picks it up.
  - Iter 9999 is astronomically above the K-buffer eviction cutoff,
    so it becomes PERSISTENT — never gets deleted by rolling cleanup.
  - "_valdrill" tag surfaces in the loader's per-source breakdown log
    so its presence is visible in training_history.

━━ Upload to cluster ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  scp -i C:\Users\henry\.ssh\id_ed25519 \

    h74liang@wato-login1.ext.watonomous.ca:~/extinction-chess/replay_buffer/

Buffer picks up the new file on the next iter's load. No cluster-side
code change needed — the replay buffer loader already reads any file
matching the iter_ regex.

To REMOVE the drilled data: delete the .npz file from the cluster's
replay_buffer/ directory. Deletion takes effect on the next iter's load.

┌─ What it does ──────────────────────────────────────────────────────────┐
│ When a game plays move M, MCTS at position P0 built a subtree rooted    │
│ at M's child that reflects visits assigned during P0's search. Without  │
│ reuse we throw it away and start MCTS from scratch at P1. With reuse    │
│ we PROMOTE that subtree to be the new root and only run                  │
│ (num_simulations - inherited_visits) additional sims to top up.         │
│                                                                         │
│ Measured savings (tools/measure_reuse_savings.py, iter 920, 800 sims,   │
│ 50 moves): 35.7% avg per-move (median 29.9%), 1.55x MCTS-work speedup.  │
│ Realistic wall-time speedup: 1.3-1.5x (GPU forward passes dominate).    │
│                                                                         │
│ vs 13.5k s/iter current: expect 9-11k s/iter with reuse ON.             │
└─────────────────────────────────────────────────────────────────────────┘

━━ Design (mirrors Python's descend_root + mcts_search reuse path) ━━━━━━━

Python reference (already in src/alphazero.py, unchanged):
  - descend_root(prev_root, moves) → walks the tree
  - mcts_search(..., prev_root=X, return_root=True) → top-up semantics
  - Bit-exact identity vs fresh proved at BATCH_SIZE_MCTS=1 in
    tools/test_reuse.py (passed Aug 2 with iter 850).

C++ port (new — src/cpp/):
  MCTS::promote(const Move& m)  (mcts.h line ~68, mcts.cpp bottom):
    1. Find root's child matching m by (from, to, promo).
    2. Guard: return false if missing, unexpanded, or visit_count==0.
    3. BFS from matched child → collect reachable node indices.
    4. Build old→new remap, rebuild nodes_ as compact vector with
       parent/first_child indices remapped, virtual_loss zeroed.
    5. Commit: root_=0, sims_done_=new-root.visit_count, clear pending.
    6. apply_dirichlet_noise_at_root() (extracted helper — shared with
       expand_root).
  Returns bool. Caller destroys the MCTS on false.

  SelfPlayManager::make_move (self_play.cpp) — with flag:
    - After playing move on pg.game:
      - If game.over or move_count >= max_moves: finish_game as before.
      - Else if use_tree_reuse_ && mcts->promote(actual_move):
          record_position(slot);   ← must be called here (bypassing
                                     NEED_ROOT_EVAL, which normally does it)
          phase = mcts->is_done() ? MOVE_READY : SEARCHING
      - Else (flag off, or promote failed):
          delete mcts; phase = NEED_ROOT_EVAL (unchanged behavior)

--- What to do when auto-benchmark misses a key iter comparison ---

The auto-battery uses a rolling window (recent = last 5 × 10-iters, distant
= 100-150 iters back). This means MID-RANGE iters (e.g. 50 iters back) are
often SKIPPED. If you need a specific comparison like "iter 870 vs iter 810"
(the rollback-threshold check), submit it manually:

sbatch --partition=compute --gres=gpu:rtx_4090:1 --cpus-per-task=4 --mem=16G --time=4:00:00 --nodelist=trpro-slurm2 --output=$HOME/compare_<NEW>vs<ANCHOR>_%j.log --wrap="export PYTHONUNBUFFERED=1 && cd ~/extinction-chess/src && python3 setup.py build_ext --inplace && python3 compare_extensive.py --m1 az_iter_<ANCHOR>_XXpct.pt --m2 az_iter_<NEW>_XXpct.pt --device cuda"

--- MODAL CLI GOTCHAS DISCOVERED DURING DEPLOY (Jul 31) ---

These caught us off-guard vs. Modal doc examples. If future-you rebuilds:

1. `modal profile create <name>` does NOT exist. Profile is auto-created
   by `modal token set --token-id ... --token-secret ... --profile <name>`.
   If you omit `--profile <name>`, Modal names the profile after the
   WORKSPACE NAME automatically (our profiles are `henryliang416525`
   and `bobbyzinger122` — the workspace names, not what we intended).

2. `modal token check` does NOT exist in Modal 1.5+. To verify auth,
   use `modal app list` — should return empty table (not an auth error).

3. `--profile` is NOT a top-level flag. `modal --profile X token check`
   fails with "No such option '--profile'". Correct pattern is env var:
       MODAL_PROFILE=<name> modal <subcommand>
   Our daemon uses this env-var approach (see run_modal() in
   modal_helper_cron.py). Old commands in this doc that show
   `modal --profile X ...` are WRONG and need this fix.

4. Cron does NOT inherit user PATH. `/home/h74liang/.local/bin/python`
   does NOT exist (only pip-installed scripts land there). Use full
   `/usr/bin/python3` in the crontab entry. `~/.bashrc` addition of
   `~/.local/bin` to PATH is for interactive shells only.

Symptom: `tail ~/modal_helper_cron.log` shows nothing new after 5+ min
  Likely: cron entry has a syntax error or wrong Python path
  Check:  crontab -l  (verify `/usr/bin/python3` path, not `~/.local/bin/python`)
          which python3  (should be /usr/bin/python3)

Symptom: Log shows "/bin/sh: 1: /home/h74liang/.local/bin/python: not found"
  Cause: crontab uses stale path
  Fix:   crontab -e, replace with /usr/bin/python3, save

Symptom: Log shows "[modal-cron] rate-limited (3/h cap), deferring iter ..."
  Cause: More than 3 processing events in the last rolling hour
  Fix:   Wait an hour, or edit config to bump rate_limit_max_events_per_hour

Symptom: `modal deploy` returns "Auth error" or "profile not found"
  Cause: MODAL_PROFILE env var not set, or profile name wrong
  Fix:   MODAL_PROFILE=<workspace_name> modal ...
         List profiles: modal profile list

Symptom: Cluster training crashes on load with numpy shape error
  Cause: A Modal file has wrong format (shouldn't happen with validate step,
         but if it does...)
  Fix:   Immediately: rm ~/extinction-chess/replay_buffer/*_modal*.npz
         Then investigate which file was bad (validate manually)
         The loader has try/except so a single bad file won't crash training
         — but if validation was skipped or file mid-write, could still fail.

Symptom: Modal helper fails during self-play with C++ import error
  Cause: modal_helper.py's build_ext step failed
  Fix:   Check helper's stdout: MODAL_PROFILE=<name> modal app logs extinction-chess-helper
         Usually a missing apt package or version mismatch.

Symptom: `modal volume put` says "volume not found"
  Cause: Volume wasn't auto-created on first invocation
  Fix:   MODAL_PROFILE=<name> modal volume create extinction-chess-ckpts
         MODAL_PROFILE=<name> modal volume create extinction-chess-helper-outputs

Symptom: `modal token check` says "No such command"
  Cause: Command doesn't exist in Modal 1.5+ (see gotchas above)
  Fix:   Use `MODAL_PROFILE=<name> modal app list` instead

--- SETUP GOTCHAS (from July 31 initial run) ---

Three surprises found during first elite run — future scripts should
build these in from the start:

1. `export PATH="$HOME/.local/bin:$PATH"` at TOP of script.
   Non-interactive scripts don't source ~/.bashrc, so `modal` isn't
   in PATH inside script. Without this, every `modal` invocation dies
   with "command not found" and produces zero elite data. (See fix
   applied on 2026-07-31 in `~/run_elite_iter920.sh`.)

2. `set -e` MUST be removed from parallel-helper scripts.
   If ANY of the 20 background `modal run` invocations returns non-zero
   (e.g. transient Modal API glitch on one helper), `wait` returns
   non-zero, and `set -e` kills the script BEFORE the download loop.
   Result: all 19 successful helpers' outputs stranded on Modal Volume.
   Fix: remove `set -e`, tolerate partial failures, download what
   actually exists. (See sed fix applied on 2026-07-31.)

3. Modal free tier is HARD-CAPPED at 10 GPUs per workspace (visible
   in workspace metrics as "Limit hit" when at 10/10). This drove the
   20-helper design: 10 per account × 2 accounts = 20. Can't launch
   more than 10 concurrent per account. If you try, they queue.
