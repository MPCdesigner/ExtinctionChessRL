== BENCHMARK TESTS (submitted from cluster shell after SSH) ==

The 4-test battery run after each new 100% checkpoint (checkpoints exist only
at multiples of 10).

PREFERRED — use trpro-slurm2 (RTX 4090). It is isolated from training
(main = delta-slurm1, helpers = trpro-slurm1), so tests never contend
with helpers for CPU cache / memory bandwidth. Verified working Jul 7.

FALLBACK — trpro-slurm1 (RTX 3090). Only use if trpro-slurm2 is down.
On trpro-slurm1, MUST add --nice=10000 so pending helpers always outrank
pending tests. Even with --nice, running tests block helper allocations
until they finish, and MCTS-heavy tests running alongside helpers cause
2-3x slowdown for both. Prefer waiting for auto-resubmit gaps between
main jobs.

Filename convention on cluster: az_iter_<N>_<WIN_PCT>pct.pt
  - Most are _100pct.pt
  - Known exceptions: iter 550_98pct.pt, iter 690_98pct.pt
  - Verify before running: ls ~/extinction-chess/models/ | grep -E "az_iter_(N|ANCHOR|100)_"

Anchor convention for Test 4: previous checkpoint that was last benchmarked
with the FULL 4-test battery, NOT necessarily the most recent 100%. Example:
iter 720 was benchmarked with iter 680 as anchor (iter 690, 700, 710 were
skipped in-between).

--- Test 1: WIN-TAKING (multi-model, ~10 min on trpro-slurm2 clean) ---
Given 200 forced-win positions, does each model find the winning move at
20/50/100/200 sim depth? Higher % = better tactical play.

Model list covers ~24 checkpoints spanning last ~240 iters + 340 + 100.
Example list used for iter 720 (Jul 5 2026):

sbatch --partition=compute --gres=gpu:rtx_4090:1 --cpus-per-task=4 --mem=16G --time=2:00:00 --nodelist=trpro-slurm2 --output=$HOME/bench_win_taking_%j.log --wrap="export PYTHONUNBUFFERED=1 && cd ~/extinction-chess/src && python3 setup.py build_ext --inplace && python3 bench_win_taking.py --models az_iter_720_100pct.pt az_iter_710_100pct.pt az_iter_700_100pct.pt az_iter_690_98pct.pt az_iter_680_100pct.pt az_iter_670_100pct.pt az_iter_660_100pct.pt az_iter_650_100pct.pt az_iter_640_100pct.pt az_iter_630_100pct.pt az_iter_620_100pct.pt az_iter_610_100pct.pt az_iter_600_100pct.pt az_iter_590_100pct.pt az_iter_580_100pct.pt az_iter_570_100pct.pt az_iter_560_100pct.pt az_iter_550_98pct.pt az_iter_540_100pct.pt az_iter_520_100pct.pt az_iter_500_100pct.pt az_iter_480_100pct.pt az_iter_340_100pct.pt az_iter_100_100pct.pt --sims 20 50 100 200 --positions 200 --hard-only --min-distance 5"

If trpro-slurm2 is unavailable, fall back to:
  --gres=gpu:rtx_3090:1 --nodelist=trpro-slurm1 --nice=10000

For future runs, keep prepending the new iters to the front and drop iters
from the tail if the list gets too long (>30 models). Always keep iter 100
as the baseline anchor.

--- Test 2: VS ADVANCED TACTICAL RANDOM (~30 min clean on trpro-slurm2) ---
Full-game play at 5 sim levels (20/50/100/200/400) against an opponent that
takes free pieces and wins in 1 when available (semi-random otherwise).
Result is total W/L/D + per-sim breakdown. Replace <NEW> with iter number.

sbatch --partition=compute --gres=gpu:rtx_4090:1 --cpus-per-task=4 --mem=16G --time=4:00:00 --nodelist=trpro-slurm2 --output=$HOME/tactical_<NEW>_%j.log --wrap="export PYTHONUNBUFFERED=1 && cd ~/extinction-chess/src && python3 setup.py build_ext --inplace && python3 bench_vs_tactical.py --model az_iter_<NEW>_100pct.pt --device cuda"

--- Test 3: VS ITER 100 (historical baseline, ~30 min clean) ---
Sanity check that the network has advanced vs a known-weak historical
checkpoint. Should be near-100% win rate. Replace <NEW>.

sbatch --partition=compute --gres=gpu:rtx_4090:1 --cpus-per-task=4 --mem=16G --time=4:00:00 --nodelist=trpro-slurm2 --output=$HOME/compare_<NEW>vs100_%j.log --wrap="export PYTHONUNBUFFERED=1 && cd ~/extinction-chess/src && python3 setup.py build_ext --inplace && python3 compare_extensive.py --m1 az_iter_100_100pct.pt --m2 az_iter_<NEW>_100pct.pt --device cuda"

--- Test 4: VS PREVIOUS ANCHOR (H2H advancement, ~30 min clean) ---
Direct comparison to the last-benchmarked checkpoint. Replace <NEW> and
<ANCHOR>. compare_extensive.py convention: m1 = older reference,
m2 = new checkpoint being tested.

sbatch --partition=compute --gres=gpu:rtx_4090:1 --cpus-per-task=4 --mem=16G --time=4:00:00 --nodelist=trpro-slurm2 --output=$HOME/compare_<NEW>vs<ANCHOR>_%j.log --wrap="export PYTHONUNBUFFERED=1 && cd ~/extinction-chess/src && python3 setup.py build_ext --inplace && python3 compare_extensive.py --m1 az_iter_<ANCHOR>_100pct.pt --m2 az_iter_<NEW>_100pct.pt --device cuda"

Fallback to trpro-slurm1 for Tests 2-4: replace
  --gres=gpu:rtx_4090:1 --nodelist=trpro-slurm2
with
  --gres=gpu:rtx_3090:1 --nodelist=trpro-slurm1 --nice=10000

--- Checking test results ---
  tail -60 ~/bench_win_taking_<JOBID>.log
  tail -60 ~/tactical_<NEW>_<JOBID>.log
  tail -60 ~/compare_<NEW>vs100_<JOBID>.log
  tail -60 ~/compare_<NEW>vs<ANCHOR>_<JOBID>.log

Find the JOBID from the "Submitted batch job <ID>" line printed by sbatch,
or from squeue -u h74liang.

--- Contention notes ---
  - Prefer trpro-slurm2 (isolated from training). Verified Jul 7.
  - On trpro-slurm2, --nice is optional — nothing to contend with.
  - Trpro-slurm1 fallback contention: tests running alongside helpers
    experience 2-3x slowdown due to shared CPU L3 cache and memory
    bandwidth. Both tests AND helpers get slower. Avoid unless necessary.
  - --nice=10000 is mandatory for trpro-slurm1 test runs so a pending
    test never blocks a helper waiting to allocate a GPU.
  - Retroactive nice bump on a pending job: scontrol update jobid=<ID> nice=10000
  - Smoke test for trpro-slurm2 before using (in case it goes down again):
    sbatch --partition=compute --gres=gpu:rtx_4090:1 --cpus-per-task=2 --mem=8G --time=00:05:00 --nodelist=trpro-slurm2 --output=$HOME/smoke_4090_%j.log --wrap="python3 -c 'import torch; assert torch.cuda.is_available(); t = torch.randn(1000,1000, device=\"cuda\"); print(\"OK:\", t.sum().item())'"

== AUTO-BENCHMARK BATTERY (fires automatically on every ×10 checkpoint) ==

After every multiple-of-10 iter save, main automatically launches 13 test
jobs + 1 aggregator on trpro-slurm2. Non-blocking — main continues to next
iter immediately. Aggregator runs after all tests complete (5-6h later)
and writes a single human-readable summary file.

Controlled by benchmark_enabled=True in ~/extinction-chess/src/run_training.py
(inside the train(...) call). See memory: benchmark_automation.

--- What runs ---
  1. 5 recent H2H tests (vs iter N-10, N-20, N-30, N-40, N-50)
  2. 5 distant H2H tests (vs iter N-110, N-120, N-130, N-140, N-150)
  3. Win-taking multi-model (recent + distant + fixed anchors 560,550,540,
     520,500,480,340,100)
  4. Tactical random test
  5. vs iter 100 baseline H2H
  6. Aggregator (sbatched with --dependency=afterany on all 13 tests)

Missing reference checkpoints are silently skipped.

--- View the aggregated summary ---

  cat ~/extinction-chess/benchmark_results/iter_<N>.txt

  # For example, for iter 780:
  cat ~/extinction-chess/benchmark_results/iter_780.txt

Summary format is a concatenation of each test's own end-of-log block, with
section headers "[i/13] category: subject (job JOBID)". Matches exactly what
raw tests print, so it's readable without regex parsing.

--- View a specific test's raw log ---

  # Individual per-test logs live in a sub-directory per iter:
  ls ~/benchmark_battery/iter_<N>/

  # Contents include:
  #   compare_<N>vs<opp>_<jobid>.log    (10 H2H logs, one per opponent)
  #   bench_win_taking_<jobid>.log      (win-taking log)
  #   tactical_<N>_<jobid>.log          (tactical random)
  #   compare_<N>vs100_<jobid>.log      (vs iter 100)
  #   aggregator_<jobid>.log            (aggregator's own log)

  tail -30 ~/benchmark_battery/iter_780/compare_780vs720_XXXXX.log

--- Verify a battery fired for a given iter ---

  # 1. Look for the "[benchmark]" lines in main's log around iter N:
  grep -A 20 "\[iter <N>\]" ~/train_<jobid>.log

  # Expected: 14 "[benchmark]" lines after the "★ new best" line —
  # one per test job launched, plus aggregator.

  # 2. Verify the summary file exists (appears ~5-6h after iter save):
  ls -la ~/extinction-chess/benchmark_results/iter_<N>.txt

  # 3. If not there yet, check remaining test jobs still running:
  squeue -u h74liang | grep trpro-slurm2

--- Rolling-window model list (recent + distant) ---

At iter N, the recent-5 opponents are iter N-10 through N-50, and the
distant-5 are iter N-110 through N-150. The lists shift by 10 for each
new benchmark. Win-taking always includes these 10 rolling opponents PLUS
the fixed anchors 560,550,540,520,500,480,340,100. Fixed anchors let us
compare current strength against historically-important checkpoints
without them being "aged out" of the rolling window.

--- Interpretation cheat sheet ---

  H2H % > 55%      → new checkpoint clearly stronger than opponent
  H2H % ~ 50%      → tied within noise (200 games has ±7% CI)
  H2H % < 45%      → new checkpoint clearly weaker (regression)

  Win-taking       → tactical acuity metric. iter 500-560 tops it due to
                     Phase-13 drilling artifact. NEVER use in isolation.

  Tactical random  → general play metric. Complements win-taking.

  vs iter 100      → baseline sanity check. Should be 65%+ for any
                     mature checkpoint.

--- Enable / disable ---

  # Check current state:
  grep benchmark_enabled ~/extinction-chess/src/run_training.py
  # (must be in ~/extinction-chess/src/ NOT ~/extinction-chess/ — see the
  # "Upload a file to cluster" section above for the path trap)

  # To disable temporarily: edit the file, set to False, SCP to src/,
  # takes effect at next auto-resubmit.


== POSITIONAL EVALUATION TOOL (local, pygame) ==

Local tool for inspecting how specific models evaluate specific positions.
Complements the aggregate benchmark battery — battery gives statistics,
this gives per-position insight.

  cd "c:\Users\henry\Desktop\Extinction Chess RL"
  python -m tools.positional_eval

Startup opens a tkinter file picker — multi-select model .pt files from
models/. Once loaded, main window opens with:
  - Board (left)
  - Palette (only in construction mode)
  - Model columns (right)
  - Settings overlay (max sims + which models to include)

Values are displayed in WHITE'S perspective: +1 = White winning, -1 =
Black winning. Does NOT flip with whose turn it is (internally the model
outputs current-player-perspective; the tool converts).

See memory: positional_eval_tool for full details.
